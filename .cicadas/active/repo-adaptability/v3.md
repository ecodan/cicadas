# Cicadas Canon V3

## Status

Draft proposal.

## Problem

The current canon model over-indexes on describing the repository and under-indexes on helping an agent make the next local change well.

That shows up in a few ways:

- Repo-wide canon is easy to generate but too high-level to be useful for most brownfield spec work.
- Separate `areas` and `modules` create taxonomy, but not necessarily actionable local context.
- The primary customer of the canon is the agent, not the human reader.
- In large repos, most initiatives, tweaks, and bug fixes are local. Agents rarely need a whole-repo architectural narrative.
- Even when the repo is very large, the agent usually needs a small, trustworthy context pack for the slice of the system that is about to change.

## First Principles

The canon exists to improve agent decisions while drafting and evolving specs.

That means the canon should optimize for:

1. Fast loading
2. Local relevance
3. Trustworthiness
4. Boundary awareness
5. Change guidance

The canon should answer, with minimal token cost:

- What is this part of the system?
- Why does it exist?
- How is it built?
- What belongs here and what does not?
- What nearby things matter?
- What invariants must not be broken?
- How should a change here be validated?

The canon should not optimize for:

- exhaustive repository narration
- architecture theater
- duplicating code structure without adding decision-useful context
- maintaining parallel documentation hierarchies that agents do not actually load

## Core Shift

V3 replaces taxonomy-first canon with locality-first canon.

The key unit of canon is no longer a generic repo `area` or a generic build `module`.

The key unit is a `slice`.

A slice is:

- a region of the codebase that tends to change together
- small enough to support local design reasoning
- large enough to include the boundaries and neighboring context needed for safe changes

A slice may correspond to:

- a single build module
- part of a large module
- several tightly coupled directories
- a cross-cutting surface that routinely changes together

The important point is that a slice is defined by change locality, not by directory taxonomy alone.

## Canon Shape

V3 uses a two-level model by default:

1. Repo-wide orientation
2. Slice-level working canon

Everything else is optional.

### 1. Repo-Wide Orientation

This should stay very small.

Suggested files:

- `canon/summary.md`
- `canon/repo-context.md`
- `canon/repo.json`
- `canon/repo-tree.jsonl`

Purpose of each:

- `summary.md`
  One dense repo-wide orientation snapshot. This exists to establish vocabulary, top-level structure, and major constraints.

- `repo-context.md`
  Compact machine-generated routing/context artifact.

- `repo.json`
  Durable planning metadata for canon strategy, repo mode, and scan results.

- `repo-tree.jsonl`
  Machine inventory, not prose canon.

Repo-wide prose should be minimal. It is just enough to help the agent locate the likely slice.

### 2. Slice-Level Working Canon

This is the real canon for brownfield work.

Suggested shape:

```text
.cicadas/canon/
├── summary.md
├── repo-context.md
├── repo.json
├── repo-tree.jsonl
└── slices/
    └── {slice-name}/
        ├── summary.md
        ├── boundaries.md
        ├── architecture.md
        ├── invariants.md
        ├── change-guide.md
        ├── interfaces.md         # optional
        ├── models.md             # optional
        ├── ux.md                 # optional
        └── routing.md            # optional
```

## Slice Files

### `summary.md`

Purpose:

- the first file loaded for a slice
- compact orientation for local design work

It should answer:

- what this slice is
- why it exists
- what kinds of changes usually land here
- what nearby slices are commonly relevant

### `boundaries.md`

Purpose:

- define ownership boundaries

It should answer:

- what belongs here
- what does not belong here
- upstream and downstream neighbors
- common wrong turns

This is one of the highest-value files because agents often fail at boundaries, not syntax.

### `architecture.md`

Purpose:

- explain the local implementation model

It should include:

- local components
- control/data flow
- extension points
- significant internal seams
- local technical constraints

This should be local, not a rewrite of whole-repo architecture.

### `invariants.md`

Purpose:

- preserve what must remain true across future changes

It should capture:

- business invariants
- technical invariants
- migration constraints
- rollout hazards
- compatibility rules
- performance/security constraints if local to the slice

This file is often more useful than a broad architecture summary.

### `change-guide.md`

Purpose:

- help the agent safely plan and validate common changes

It should include:

- common change patterns
- where to start in code
- which tests to run first
- what kinds of specs usually need updates
- whether changes here often imply neighbor changes

This should be practical, not descriptive.

### Optional files

Only create these when they materially help.

- `interfaces.md`
  For slices with important API contracts, request/response shapes, events, CLI surfaces, or extension contracts.

- `models.md`
  For slices with important schemas, persistence rules, domain models, or transport contracts.

- `ux.md`
  For slices where user experience and interaction states materially influence spec writing.

- `routing.md`
  For especially large or internally complex slices where there is still local routing ambiguity.

## What Happens to Areas and Modules

V3 does not make `areas` and `modules` first-class required entities.

Instead:

- a build-defined module may become a slice if it is a good unit of change locality
- a former area may become a slice if it is a good unit of change locality
- cross-cutting routing notes may remain, but only when they add real value

In other words:

- `module` is an implementation fact
- `area` is a routing heuristic
- `slice` is the canon unit

That keeps the canon tied to the work the agent is doing rather than to taxonomy.

## Slice Selection Rule

When bootstrapping or evolving canon, create slices based on likely change locality.

Good slice criteria:

- changes frequently cluster here
- this region has meaningful local boundaries
- local invariants matter
- the agent can do useful spec work after loading this slice plus repo summary

Bad slice criteria:

- “this is a directory”
- “this is a build module” with no local design value
- “this is a broad category” that still leaves the agent guessing

## Loading Model

The loading model should be simple and deterministic.

### Default load for brownfield spec drafting

1. `canon/summary.md`
2. `canon/repo-context.md`
3. the most relevant slice `summary.md`
4. that slice's `boundaries.md`
5. that slice's `architecture.md`
6. that slice's `invariants.md`
7. optional slice files only if needed

### Escalation rules

Load neighboring slices only when:

- the boundary is unclear
- the planned change crosses a local interface
- rollout or migration impacts spill into adjacent code
- validation requirements obviously span slices

Do not load broad repo canon by default if one slice pack is enough.

## Bootstrap Guidance

Bootstrap should not try to write full local canon for the whole repo in one pass.

That is too expensive and tends to produce shallow summaries.

Instead bootstrap should:

1. run `scan-repo`
2. block until scan completion
3. generate minimal repo-wide orientation
4. identify candidate slices
5. deeply document only the first set of high-value slices
6. leave the rest as deferred slice candidates

This means bootstrap becomes:

- shallow globally
- deep selectively

That is a better trade for agent usefulness.

## Candidate Slice Strategy

For a mega-repo, initial bootstrap should produce:

- one repo summary
- a small number of high-value slices
- a deferred list of future slices

The first slices should be chosen by:

- frequency of likely change
- strategic importance
- amount of local complexity
- likelihood that future spec work will start there

For example, a mega-repo might begin with:

- a few core product slices
- one or two platform slices
- one infrastructure slice with high blast radius
- one cross-cutting slice only if it frequently changes together

Not every top-level directory needs a slice on day one.

## Ongoing Evolution

Canon should deepen incrementally through real work.

When an initiative touches a slice:

- refresh that slice's local canon
- add missing local files if the change revealed a gap
- create a new slice only if the current slice is too broad for future safe work

That means canon growth is demand-driven.

## Relationship to Code Graph

A future code graph changes the routing problem but not the local-canon problem.

Graph is best for:

- adjacency
- dependency traversal
- call paths
- likely neighboring surfaces

Slice canon is best for:

- why this region exists
- what boundaries matter
- what invariants must hold
- what kinds of changes are common or dangerous
- what validation pattern is expected

So the graph should reduce the need for broad routing prose, but it should not replace local working canon.

If graph becomes strong enough, the repo-wide layer can shrink further:

- `summary.md`
- graph-derived routing
- slice canon for local reasoning

## Proposed Metadata Changes

`repo.json` should evolve to describe slices directly.

Suggested shape:

```json
{
  "repo_mode": "mega-repo",
  "canon_strategy": "locality-first",
  "slice_strategy": {
    "unit": "slice",
    "bootstrap_mode": "shallow-global-deep-selective"
  },
  "candidate_slices": [
    {
      "name": "jira-domains-platform-automation",
      "paths": ["jira-domains/platform/automation"],
      "status": "ready"
    },
    {
      "name": "jira-service-management-surface",
      "paths": [
        "jira-domains/product/jira-service-management",
        "jira-components/jira-plugins/jira-servicedesk"
      ],
      "status": "candidate"
    }
  ]
}
```

## Templates

V3 needs slice templates instead of area/module templates.

Suggested templates:

- `slice-summary.md`
- `slice-boundaries.md`
- `slice-architecture.md`
- `slice-invariants.md`
- `slice-change-guide.md`
- `slice-interfaces.md`
- `slice-models.md`
- `slice-ux.md`

These should be optimized for agent consumption, not generic documentation completeness.

## Operational Rules

### Rule 1

Do not create a canon entity unless an agent would realistically load it during spec work.

### Rule 2

Prefer one strong local slice pack over several weak overlapping summaries.

### Rule 3

Do not create parallel hierarchies that describe the same region from different naming systems unless there is clear value.

### Rule 4

If a file does not help an agent decide or design, it is probably the wrong file.

### Rule 5

When in doubt, write local boundaries, invariants, and change guidance before writing broader architecture prose.

## Migration from V2

### Step 1

Keep:

- `canon/summary.md`
- `repo-context.md`
- `repo.json`
- `repo-tree.jsonl`

### Step 2

Stop requiring separate first-class `areas/` and `modules/`.

### Step 3

Map existing useful docs into initial slices.

### Step 4

Delete or merge duplicate routing/module docs that describe the same locality.

### Step 5

Make future canon synthesis slice-oriented.

## Success Criteria

V3 is working if:

- an agent can draft a localized tweak or bug spec from repo summary plus one slice pack
- slice docs are specific enough to guide actual design choices
- the canon grows deeper through real work instead of broad one-time summarization
- duplicate high-level summaries shrink over time
- graph plus slice canon together outperform repo taxonomy prose

## Short Version

V3 should move Cicadas canon from:

- “describe the repository”

to:

- “provide the smallest trustworthy local context pack an agent needs to design the next change”

That means:

- minimal global orientation
- strong local slice canon
- boundaries and invariants over taxonomy
- demand-driven depth
- optional routing overlays, not required parallel structures
