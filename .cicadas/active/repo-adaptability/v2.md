# Cicadas Bootstrap V2 Requirements

## Overview

Cicadas Bootstrap V2 should treat brownfield bootstrap as a research, planning, synthesis, and QA workflow rather than a single scan-and-dump pass. It must work reliably across small repos, large repos, and true mega repos, with special attention to LLM context limitations and routing difficulty.

This version should focus on:
- better repo classification
- build-first structure discovery
- canon strategy selection
- bootstrap planning/tasks
- canon generation
- canon QA

This version does not need to fully solve post-change canon updates yet, but it should avoid painting us into a corner.

## Problem Statement

The current bootstrap flow underestimates very large monorepos because classification relies too heavily on narrow path heuristics like “runtime paths” and “ownership zones.” This fails on repos whose meaningful structure is declared by build systems rather than conventional directory shapes.

For LLM-driven work, raw scale matters:
- larger repos are harder to load into context safely
- routing mistakes become more expensive
- flat canon becomes less useful as repo scale grows
- bootstrap must choose the right canon structure before writing docs

Bootstrap therefore needs stronger evidence gathering, explicit judgment, and a more robust planning step before synthesis.

## Goals

1. Correctly classify repo scale and routing complexity for LLM use.
2. Prefer declared structure over inferred structure.
3. Produce the right canon shape for the repo, not a one-size-fits-all canon.
4. Generate a bootstrap task plan before canon synthesis.
5. Produce canon that is useful for routing and safe brownfield edits.
6. QA the canon against code/build evidence before declaring bootstrap complete.

## Non-Goals

1. Full redesign of ongoing canon maintenance after implementation changes.
2. Full dependency-graph or symbol-graph analysis for every build system.
3. Perfect semantic ownership inference from code authorship or org metadata.
4. Exhaustive module-level canon for every leaf in giant repos.

## Core Principles

1. Size matters. Repo scale must be a first-class signal because LLM context capacity is limited.
2. Declared structure beats inferred structure. Build/workspace/module definitions should be used before directory-name heuristics.
3. Canon shape should be chosen, not assumed. Bootstrap must decide whether the repo needs flat canon, routed canon, or hierarchical canon.
4. Routing utility matters more than documentation completeness. Canon should optimize for helping future agents find the right working set quickly.
5. Brownfield bootstrap is a staged workflow. Bootstrap should explicitly separate scan, analysis, planning, synthesis, and QA.

## Functional Requirements

### 1. Evidence Gathering Phase

Bootstrap must gather evidence before classifying or generating canon.

It must collect:
- repo file count
- meaningful file count
- estimated LoC
- top-level directory breadth
- language distribution
- build/workspace systems present
- declared build modules/workspaces/subprojects
- major test surfaces
- runtime/deployment/package surfaces
- existing docs and READMEs
- major tool/runtime versions where easy to detect

Meaningful files should exclude obvious generated or local-only areas.

Bootstrap should prefer cheap, scalable evidence collection that works on very large repos.

### 2. Build-First Structure Discovery

Bootstrap must start by detecting the build/workspace structure when available.

Supported patterns should eventually include:
- Maven multi-module
- Gradle multi-project
- Bazel
- pnpm/yarn/npm workspaces
- Cargo workspaces
- other common monorepo systems as practical
- non-monorepos build with any other build system (e.g. UV)

For each detected build system, bootstrap should identify:
- major module families
- likely outputs
- likely test modules
- likely packaging/runtime modules
- top-level structural partitions

Build-defined partitions should be treated as primary structural signals.

### 3. Repo Classification

Bootstrap must classify repos using both scale and structure.

Classification must consider at least:
- meaningful file count
- estimated LoC
- declared module/workspace count
- number of major structural partitions
- number of test surfaces
- number of runtimes/build systems/languages
- routing complexity

Scale must establish a minimum class.

Recommended floors:
- `normal-repo`: under 1K meaningful files and under 100K LoC
- `large-repo`: 1K+ meaningful files or 100K+ LoC
- `mega-repo`: 25K+ meaningful files or 2M+ LoC

Exact thresholds may be configurable, but size must be sufficient on its own to force promotion.

Topology/structure should be able to promote a borderline repo, but should not demote a clearly huge repo.

### 4. Replace Confusing Heuristics

Bootstrap should stop using narrow, hard-to-understand concepts as the primary deciders.

Terms like:
- `ownership_zone_candidates`
- `runtime_paths`

should be replaced or demoted in favor of clearer concepts such as:
- major code zones
- working areas
- routing surfaces
- declared partitions
- runtime/package surfaces

If older internal terms remain for compatibility, user-facing outputs should use clearer language.

### 5. Canon Strategy Selection

After evidence gathering and classification, bootstrap must choose a canon strategy.

Supported strategies:
- flat canon for small repos
- routed canon for large repos
- hierarchical canon for mega repos with strong partition structure

The strategy decision should explicitly answer:
- what root-level docs are needed
- whether area docs are needed
- whether module snapshots are full or selective
- whether hierarchical canon partitions are needed
- what detail should live at root vs sub-area level

Bootstrap must record this plan before generating canon.

### 6. Hierarchical Canon Support

Bootstrap should support hierarchical canon selection for large monorepos.

This does not require separate registries or separate Git repos.

It does require the ability to define:
- root canon for global orientation
- partition canon for major build-defined areas
- optional deeper canon for especially large subtrees

Example shape:
- root repo canon
- major partition canon
- optional nested partition canon

Root canon should stay small and routing-oriented. Most detailed canon should live in the relevant partition.

Sub-canons should have their own directories with files that map to general canon so they can operate semi-independantly. That said, they should be aware of root canon.

### 7. Bootstrap Planning / Task Generation

Before writing canon, bootstrap must generate a bootstrap plan or task list.

The plan must identify:
- detected repo mode
- chosen canon strategy
- root docs to generate
- area/partition docs to generate
- selective module snapshots to generate
- deferred areas
- validation steps
- open questions / insufficient-context items

This plan can be internal or written to disk, but it must exist as a discrete step.

### 8. Canon Generation

Bootstrap must generate canon based on the selected strategy.

Root canon should generally include:
- product overview
- tech overview
- routing guide
- compact summary
- repo context

For large or mega repos, bootstrap should also generate:
- area docs
- selective module snapshots
- partition-oriented routing guidance

For hierarchical strategies, bootstrap should generate root-level orientation plus partition-level docs.

Canon must be grounded in evidence from code/build/docs, not speculation.

When evidence is insufficient, bootstrap must say so explicitly rather than inventing details.

### 9. Canon QA / Validation

Bootstrap must QA the canon before completion.

Validation should include:
- docs exist where the selected strategy said they would
- routing guidance points to real areas
- major build-defined partitions are represented
- obvious structural surfaces are not omitted
- links are valid
- claims do not contradict gathered evidence
- insufficient-context placeholders are used where appropriate

For large and mega repos, QA should explicitly verify that the produced canon is usable for routing, not just present on disk.

### 10. Bootstrap Output Summary

At completion, bootstrap should provide a concise summary including:
- scale findings
- detected build/workspace structure
- chosen repo mode
- chosen canon strategy
- generated canon artifacts
- deferred/open questions
- any classifier uncertainty

## Heuristic Requirements

### Scale Signals

Bootstrap must compute:
- meaningful file count
- estimated LoC
- language counts
- top-level fanout
- module/workspace counts

These scale signals must influence classification directly.

### Structure Signals

Bootstrap should compute:
- build-defined partitions
- packaging/runtime surfaces
- test surfaces
- area fanout
- module family repetition
- number of independent working areas

These structure signals should influence routing and canon strategy.

### Final Decision Rule

Repo mode should be based on:
- a scale floor
- then structural/routing promotion
- not the other way around

Conceptually:
- `repo_mode = max(scale_class, topology_class)`

## UX / Developer Experience Requirements

1. Bootstrap should surface progress in phases.
Examples:
- discovering build systems
- collecting scale metrics
- extracting module structure
- choosing canon strategy
- generating docs
- validating docs

2. Bootstrap should explain why it classified the repo the way it did. This explanation should be understandable to a human.
3. Bootstrap should explain why it chose a given canon structure. Especially important for hierarchical decisions.
4. User-facing language should avoid jargon that is not self-explanatory. Terms like “ownership zones” should not be the main explanation.

## Data Model / Artifact Requirements

Bootstrap should produce or maintain machine-readable metadata for:
- repo scale
- detected build systems
- declared partitions
- chosen canon strategy
- generated canon targets
- validation results

This metadata should be usable later by future canon-update workflows.

## Open Design Questions Deferred To Future Work

1. How canon updates should work after code changes in a hierarchical canon structure.
2. Whether partition canons should have independent lifecycle/state or remain under one global Cicadas registry.
3. How deep hierarchical partitioning should go automatically.
4. Whether build graph adjacency or dependency graph analysis should be added later for better routing and blast-radius analysis.

## Success Criteria

Bootstrap V2 is successful if:
- a repo with 1M+ LoC or 10K+ meaningful files is never classified below `mega-repo`
- build-defined module structure meaningfully shapes the canon plan
- large monorepos produce routing-oriented canon, not just flat overviews
- bootstrap emits a clear plan before synthesis
- canon covers the major working partitions of the repo
- the final explanation makes the classification and canon structure understandable to a human reviewer

## Recommended Implementation Order

1. Add scale metrics and scale floors.
2. Make build-system discovery the first structural step.
3. Refactor classification to combine scale + structure.
4. Add explicit canon strategy selection.
5. Add bootstrap planning/tasks artifact.
6. Add hierarchical canon support.
7. Add stronger canon QA.
8. Revisit post-change canon maintenance in a follow-up version.
